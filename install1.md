## Resolution (2026-11-03) — why it broke, and what now makes `apt install opencode` work

**1. dpkg phantom record.** `opencode 2.0.31` was marked installed, but `$PREFIX/bin/opencode`
(~270 MB) no longer existed (disk was at 98 %); only `lib/opencode/libopencode-crhandler.so`
was left. No apt repo carries `opencode`, so the candidate came solely from
`/var/lib/dpkg/status` → `apt install opencode` was a permanent no-op.
Fixed with `dpkg -P --force-all opencode`.

**2. pacman 404 / checksum failure = stale DB vs rebuilt asset.** The device's
`hope2333.db` (mtime 02:12, from `Push261026`) pinned `opencode-2.1.4-1` = 76 455 388 B,
sha256 `617bdd1d…`; `Push261103` republished the *same filename* rebuilt as 76 380 384 B,
sha256 `a0c174c2…`. Download succeeds, hash never matches. `install_official.sh` only runs
`pacman -Sy`, so the stale entry survives. The trailing `hope2333.github.io` mirror serves
only the DB — package URLs there 404.

**3. A local APT repo was added, because no published apt index carries `opencode`:**
- `$PREFIX/var/lib/hope2333-apt/` — flat repo: `opencode_<ver>_aarch64.deb`, `Packages`, `Packages.gz`
- `$PREFIX/bin/opencode-apt-sync` — pulls the newest `opencode_<ver>_aarch64.deb` from the
  GitHub release, verifies GitHub's sha256 digest, prunes old debs, rebuilds the index
- `$PREFIX/etc/apt/sources.list.d/hope2333-local.list` —
  `deb [trusted=yes arch=aarch64] file:///data/data/com.termux/files/usr/var/lib/hope2333-apt ./`
- `$PREFIX/etc/apt/apt.conf.d/90-opencode-local` — refreshes that index before `apt update`
  (at most once per 12 h, `OPENCODE_APT_MAX_AGE` overrides; failures never block `apt update`)

Daily use:
```sh
apt update && apt install opencode      # install / upgrade
apt install --reinstall opencode        # repair a deleted or corrupt binary
opencode-apt-sync                       # pull the newest .deb now (no apt update needed)
```

**Left untouched on purpose:** the pacman local DB still contains sync-style entries
(`%FILENAME%`/`%MD5SUM%` … warnings) copied for dpkg-owned packages, and dpkg + pacman both
"own" files like `bin/bash`. Do not run `pacman -Syu` on this install — it can overwrite the
apt-managed Termux base. The pacman mirror drift above (item 2) is a repo-publishing issue,
not a device issue.

## TUI crash fixed on-device (2026-11-03) — heap-tag interposition shim

**Root cause** (verified on this Android 11 / API 30 device): bionic scudo tags every
heap pointer in the top byte (`malloc` → `0xb400007f…`). opentui 0.8 returns such a
pointer from `ot_context_create` and converts it to a JS number; anything > 2^53
trips its guard → "Pointer exceeds safe integer range" → TUI dies. Affects every
2.1.0+ build (ot_ctx ABI); 2.0.31 (legacy ABI) never crosses heap pointers as
numbers, which is why it works. The clean fix `mallopt(M_BIONIC_SET_HEAP_TAGGING_LEVEL, NONE)`
needs **API 31** — on API 30 it returns 0 and the tag stays. scudo *validates* tags
in free/realloc ("Pointer tag … was truncated"), so pointers can't just be untagged.

**Shim** (`$PREFIX/lib/opencode/libnoheap.so`, 14 KB, source `$PREFIX/tmp/noheap.c`):
interposes malloc/calloc/realloc/reallocarray/memalign/aligned_alloc/valloc/pvalloc/
posix_memalign/free/malloc_usable_size — strips the tag byte on the way out to the
app, restores it before the real allocator sees the pointer. Tag value is sampled
live at startup; on Android 12+ mallopt succeeds inside the shim and everything
degrades to a passthrough. Verified: 20 k alloc/free stress, bash/ls, TUI alive
45 s (0 crash lines).

**Installed layout** (jcz2020/opencode-termux wrapper pattern):
- `$PREFIX/bin/opencode` → 1 KB bash wrapper: `LD_PRELOAD=…libnoheap.so` + `exec opencode.real`
- `$PREFIX/bin/opencode.real` → the dpkg-owned 2.2.5 binary, untouched
- `dpkg -V opencode` will flag `bin/opencode` (cosmetic)

**Caveats**
- After an apt upgrade, dpkg overwrites the wrapper with the plain binary → crash
  returns. Re-apply:
  ```sh
  mv $PREFIX/bin/opencode $PREFIX/bin/opencode.real
  cat > $PREFIX/bin/opencode <<'W'
  #!/data/data/com.termux/files/usr/bin/bash
  LD_PRELOAD="${PREFIX:-/data/data/com.termux/files/usr}/lib/opencode/libnoheap.so${LD_PRELOAD:+:$LD_PRELOAD}"
  export LD_PRELOAD
  exec "${PREFIX:-/data/data/com.termux/files/usr}/bin/opencode.real" "$@"
  W
  chmod 755 $PREFIX/bin/opencode
  ```
- Never run `opencode upgrade` (it would replace the wrapper with upstream's
  binary); upgrade via apt only.
- Rollback: `mv $PREFIX/bin/opencode.real $PREFIX/bin/opencode`
  (and optionally `rm $PREFIX/lib/opencode/libnoheap.so`).
- Children inherit `LD_PRELOAD`; running proot/glibc binaries from within opencode
  just prints a harmless "cannot be preloaded" warning.
- Proper long-term fix belongs in the Hope2333 build (fold the shim in like the
  seccomp crhandler), since Android 11 devices cannot use the mallopt route.

## Correction (2026-11-04): oscar's "stock -2 passes" was a false positive

The 25 s smoke window was shorter than the failure: on oscar (Android 10 /
kernel 4.4) 2.2.5-2's background server fails at ~36 s with
`Error: Failed to start server (cause: EBADF: bad file descriptor, pidfd_open)`
— the minimal crhandler answers the trapped pidfd_open with -ENOSYS and the
newer bun base then uses the dead fd (EBADF), instead of 2.2.5-1's
"Unknown Error, pidfd_open". The TUI sat alive through the 25 s window, so the
smoke wrongly passed and the device was left stock with a broken TUI.

Fixed methodology: smoke now runs 75 s AND fails on any failure signature
(pointer error, Failed to start server, pidfd_open/EBADF, ETIMEDOUT,
cli process failed) regardless of exit code. Escalation ladder extended with
the EBADF signature → installs the emulating crhandler v2 (fake pidfd is a
working fd, so spawn succeeds). Phone re-tested with the 75 s probe: clean
(kernel 4.14 answers pidfd_open with plain ENOSYS, which bun handles).

oscar went off the hotspot overnight (no route) before the fix could be
applied there; staged and pending: scp updated script + crhandler v2 .so,
run probe. Phone: stock 2.2.5-2, verified clean, 7.7 GB free.

## Resolution (2026-11-04): second false positive found and fixed

Three probes on oscar with `--print-logs` showed the real failure mode with
stock 2.2.5-2 + the minimal crhandler: **no error at all**, the TUI just parks
at `Starting background server...` — log stays at ~80-230 bytes, zero escape
sequences, process alive (so both the 25 s and the signature-based 75 s smoke
called it a PASS; "alive" was never "working").

Installing the emulating crhandler v2 made the TUI render immediately
(smoke log 228 B -> 17 KB with screen control sequences). Root cause unchanged:
kernel 4.4 + seccomp trap on pidfd_open (434); the minimal shim answers -ENOSYS
and this bun base then cannot get a usable child fd, so the background server
never comes up. (Your manual run showed the same thing once the spawn path
surfaced it: `EBADF: bad file descriptor, pidfd_open`.)

Smoke methodology, final form:
- 75 s window (failure can take ~36 s)
- fail on any failure signature, and
- fail when the log shows no rendered UI (fewer than 4 escape sequences),
  which catches the silent stall; that stall is routed to the crhandler-v2
  escalation step.

Verified end-to-end on oscar: restore stock minimal shim (8104 B) -> run script
-> "trap-gap stall detected: no UI drawn" -> crhandler v2 compiled on-device
(11672 B) -> "OK: TUI rendered" -> opencode v2.2.5 running. Phone re-tested with
the stricter smoke: stock 2.2.5-2, no wrapper, no shims (kernel 4.14 answers
pidfd_open with plain ENOSYS, which bun degrades from).

Standing caveat: the crhandler fix lives in a dpkg-owned path, so every
`dpkg -i` / `apt upgrade` of opencode reverts oscar to the minimal shim. Re-run
`opencode-tui-fix.sh` after any upgrade (it is idempotent and self-retiring on
devices that do not need it).
